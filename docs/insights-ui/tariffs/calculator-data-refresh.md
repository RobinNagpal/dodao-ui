# Tariff Calculator Data Refresh (official-source measures)

Runbook for refreshing the data the tariff calculator's official-source engine reads (issue #1785): every Chapter 99 heading, the reviewed extra-duty measures, and the base rates in `hts_codes`. Run it for each new HTS revision and whenever a Federal Register / CBP CSMS action adds, changes or ends a measure.

Nothing here writes to a database from a laptop (only the lines-sync generator reads it, see "Syncing hts_codes lines with a new HTS edition"). Scripts produce **committed JSON + a generated SQL file**; the SQL is reviewed in a PR and applied by a GitHub workflow (dry run first).

## 1. Get the HTS JSON

The newest revision is at `https://www.usitc.gov/sites/default/files/tata/hts/hts_<year>_revision_<n>_json.json` (`pnpm tariff:validate-chapters --check-hts` tells you whether a newer one exists). usitc.gov often answers scripted requests with **403 Access Denied**; the scripts send a browser User-Agent and retry with delays, and cache successful downloads under the OS temp dir. If it still refuses, download the file in a browser and pass `--file` / `--hts-file`.

## 2. Regenerate (from `insights-ui/`)

```bash
# Chapter 99 headings → src/tariff-data/calculator/ch99-headings.json
pnpm tariff:build-ch99 --file ~/Downloads/hts_2026_revision_21_json.json
#   or: pnpm tariff:build-ch99                              (newest revision on usitc.gov)
#   or: pnpm tariff:build-ch99 --edition "2026 Revision 21"
#   --edition is needed with --file when the filename isn't hts_<year>_revision_<n>_json.json

# FTA quota headings → src/tariff-data/calculator/fta-quota-headings.json (bundled; no SQL, no DB rows)
pnpm tariff:build-fta-quota --file ~/Downloads/hts_2026_revision_21_json.json   # --published YYYY-MM-DD for a new revision

# Re-extract product coverage from the Chapter 99 U.S. notes (needs pdftotext or Python + pypdf):
npx tsx src/scripts/tariff-calculator/extract-ch99-note-coverage.ts   # → note-coverage.json
# Update the reviewed definitions (new/changed/ended measures, dates, sources, htsEdition, reviewedAt) in
# src/scripts/tariff-calculator/build-measures.py, then rebuild measures.json from them + note-coverage.json:
python3 src/scripts/tariff-calculator/build-measures.py && npx prettier --write src/tariff-data/calculator/measures.json
# Never hand-edit measures.json: it is regenerated by build-measures.py — see §3.

# One SQL file for headings + measures + base rates
pnpm tariff:build-data-sql --hts-file ~/Downloads/hts_2026_revision_21_json.json
#   --no-base-rates   headings + measures only
#   --out <path>      different output path

# Base rates only (standalone transaction), when nothing else changed
pnpm tariff:build-base-rates-sql --file ~/Downloads/hts_2026_revision_21_json.json
```

`tariff:build-ch99` prints counts per `rateKind`, how many headings have countries / excepted headings / note references, and every heading whose rate it could not parse (`rateKind: "unknown"`). Unknowns are expected for:

- headings with a blank rate column (quota sub-headings such as `9903.17.*`, `9903.18.*`, `9903.52.*`; sanctions/column-2 headings such as `9903.90.08`);
- specific or partial rates: "+ a duty of 25% upon the value of the non-U.S. content", "The duty provided in subheadings 8716.39.00, … + 100%".

A measure that uses such a heading carries its own `rateKind` / `ratePct` in `measures.json`; the heading row is reference data.

How the parser reads a heading:

| Field                  | Rule                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `rateKind` / `ratePct` | "The duty provided in the applicable subheading + 25%" (also "+25%", "plus 25%", "+ a duty of 25%") → `additive` 25; "10%" → `flat` 10 (in place of the base rate); "Free" → `flat` 0; "The duty provided in the applicable subheading" or "No change" → `relief`; anything else → `unknown`.                                                                                                                                                                                                                                                                                      |
| `countries`            | Every country named in the description (names from `src/utils/tariff-calculator/countries.ts` plus HTS spellings such as "Republic of the Congo", "Türkiye", "Côte d\`Ivoire", "Hong Kong, China" → HK); "European Union" (incl. "a member state of the European Union", "a European Union member country") → the 27 member states. Indented headings with no country of their own inherit the countries named in their parent rows (e.g. `9903.89.05` under "Articles the product of France, of Germany, of Spain or of the United Kingdom:"). The United States is never listed. |
| `exceptCodes`          | Headings after "Except for products described in headings …", "except as provided for in headings …", "Except as provided in heading …" (every clause in the description). Ranges are expanded: `9903.05.85–9903.05.92` → each code; a range that crosses groups (`9903.05.99–9903.06.01`) runs to `.99` and restarts at `.01`.                                                                                                                                                                                                                                                    |
| `noteRefs`             | U.S. notes to subchapter III: "U.S. note 2(a)" → `2(a)`; "subdivision (v)(iv) of U.S. note 2" → `2(v)(iv)`; "subdivisions (c) and (d) of U.S. note 40" → `40(c)`, `40(d)`; "subdivisions (v)(vi) through (v)(xvi)" → `2(v)(vi)–(v)(xvi)`; "notes 20(f) or 20(g)" → both. General notes, statistical notes and notes to other chapters are skipped. Typos are kept verbatim (`9903.01.15` cites "note 2(I)").                                                                                                                                                                       |

## FTA quota claims ("See 98xx / 99xx" special rates)

About 200 HTS lines (beef, dairy, sugar, sugar-containing products, peanuts, tobacco; chapters 2, 4, 12, 15, 17–24, 30) don't state a rate for some trade partners. Their special column points to Chapter 98/99 headings instead, e.g. 0201.10.50 "See 9822.04.01-9822.04.03 (AU)". `pnpm tariff:build-fta-quota` reads every such reference from the HTS JSON and writes the referenced headings to `fta-quota-headings.json`; the engine (`src/utils/tariff-calculator/fta-quota.ts`) prices a claim from the line's own special column (already in `hts_codes`) plus that bundled file, so **no database write is needed**.

| Field         | Rule                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `kind`        | Nearest text first (the heading, then the indented text above it): "Other" or "Goods provided for in note N(b)(2)" → `overQuota`; "quantitative limit(s/ations)" / "aggregate quantity" → `inQuota`; otherwise `unconditional`. Reviewed overrides in the script: 9822.04.02 = `safeguard` (note 8(c)); 9921.01.01/.02 (JP) = `notModelled`. A rate the parser can't read → `notModelled` (9822.09.22/.24, PA fuel ethanol). |
| `countries`   | USMCA (subchapter XXIII): note N(a) / "Goods of Mexico" → MX, note N(b) / "Goods of Canada" → CA. P+ "Of Costa Rica:" → CR. Otherwise the program's countries.                                                                                                                                                                                                                                                               |
| `subheadings` | 8-digit subheadings named in the heading's own description (per-subheading over-quota rates such as 9823.01.03). A reference's only heading of a kind is used even if its list misses the line (some lists predate renumbering, e.g. 1901.10.16 → 9822.04.25).                                                                                                                                                               |
| `noteRef`     | The U.S. note the quota/safeguard text cites ("8(b)", "1(b)(2)"); general and statistical notes are skipped. Over-quota "Other" headings take the note of the in-quota heading before them.                                                                                                                                                                                                                                  |
| `effectiveTo` | Subchapter end dates from note 1 (reviewed constants): Israel VIII and Colombia XVIII 2026-12-31, Panama XIX 2028-12-31. After it the claim is an error.                                                                                                                                                                                                                                                                     |

How a claim is priced: the tiers for the country are in-quota, a second quota (Panama milk powder / cheese, notes 4(b) / 6(b)), safeguard, over-quota — or the line's **general rate** above the quota when the agreement has no over-quota heading (most AU dairy, Israel, Morocco, Peru, Colombia, Panama and CAFTA-DR sugar). Registry facts in `confirmation-facts.json` pick the tier: `ftaWithinQuota`, `ftaWithinSecondQuota`, `ftaSafeguardApplies`, all **default "no"** (unanswered = over-quota rate, never a guessed in-quota rate). When every tier has the same rate (Colombia dairy/tobacco, Panama beef — quotas ended) or the heading is unconditional (Mexico 9823.xx.01), it is priced directly and nothing is asked. The base duty line names the heading and the U.S. note and says which answers were assumed. The requirements route offers these programs per country (USMCA → separate Mexico and Canada entries) and lists the quota questions first. Two more rules: a USMCA claim charged above the quota at a dutiable 9823 rate does not get the Canada/Mexico Section 301 relief (notes 52(g)/(h) cover goods "entered free of duty" under USMCA); and a claim charged at the general rate counts as no claim for measure conditions (the goods enter at column 1-general).

The script prints every reference with its tiers per country and anything it can't price; re-run it per HTS revision and re-check `EFFECTIVE_TO` and `KIND_OVERRIDES` against the Chapter 98/99 notes.

Review notes for these measures:

- **Chapter 30 pharmaceutical use is presumed.** The 7 Chapter 30 lines on the 52(e) / 50(a)(v) lists (`*-pharma-use-ch30`) stay unconditional. Chapter 30 is "Pharmaceutical products": headings 3003/3004 are medicaments and heading 3006 covers the pharmaceutical goods of chapter note 4, so the classification itself establishes the pharmaceutical use. This matches the Chapter 30 content file and its golden scenarios. 3006.92 (waste pharmaceuticals) is presumed the same way. The Chapter 28/29/32/34/35/38/39 lines need the confirmation.
- **Section 232 headings are mutually exclusive** (note 40(a)), and the lowest applicable rate wins (Proclamation 11020 clause 8). Relief/company measures therefore list the 232 headings they displace in `replacesCodes`. Only 9903.04.60–9903.04.66 also displace the 2026 Section 301 and Brazil duties (notes 52(f)(8), 50(a)(vi)(8)). 9903.04.67, .68 and .70 do not.
- **Note 52(i) is modelled** as `s301-2026-cafta-dr-textiles` (heading 9903.05.95, from July 24, 2026). It removes the 2026 Section 301 duty of Costa Rica, the Dominican Republic, El Salvador, Guatemala, Honduras and Nicaragua (9903.05.33, .34, .37, .40, .42, .58) from "a textile or apparel good as defined in subdivision (d)(v) of general note 29 … entered free of duty under" CAFTA-DR, so it applies only when SPI `P` / `P+` is claimed. General note 29(d)(v) defines the goods as those listed in the Annex to the WTO Agreement on Textiles and Clothing (HS 1992 six-digit codes), minus the Annex 3.29 goods it names. Coverage = the Annex lines that map exactly to Revision 21: 5004–5007, 5105–5113 (not 5105.40), 5204–5212, 5306–5311 (not coir yarn 5308.10 or paper yarn 5308.90.10), chapters 54–62, 6301–6309, and umbrellas 6601. The Annex leaves out raw fibres and waste (5001–5003, 5101–5104, 5201–5203, 5301–5305) and rags (6310). Not modelled, so the duty is still charged: the Annex's "ex" entries for textile luggage and handbags (4202), glass-fibre yarns and woven fabrics (7019) and textile quilts, comforters and cotton pillows (9404), because HS 2007/2022 restructured those subheadings or the line doesn't settle the material test. For Guatemala and El Salvador, the 52(j)(6)(iii)/(7)(iii) lists also cover many of those lines.
- After a new HTS revision, re-check: the CAFTA-DR SPI codes; the 9903.04.64 rate step (100% from April 2, 2030); the 9903.04.65 expiry (January 20, 2029); and whether Commerce/BIS has published the Annex II/III company lists (phase B of #1790: verified company lists instead of self-declaration).

**Never overwrite a SQL file that is already on `main`.** It may already have been dry-run or applied. `tariff:build-data-sql` writes `<YYYYMMDD>-<edition>.sql`. If that name already exists on `main`, rename the new output to something descriptive (e.g. `20261009-2026-revision-21-conditional-exemptions.sql`) and restore the old file. Each file replaces the tables wholesale, so applying the newest file is enough.

- `spiNotClaimed`: the measure applies only when none of the listed SPI codes is claimed; `'*'` means no SPI claimed at all (goods entered at column 1-general). Used by the Nicaragua records (9903.89.01) with `['*','P','P+']`.

### Certified (opt-in) vehicle parts: review notes

- **What they are.** Proclamation 10984 clause 12 (90 FR 48451) lets the importer of record _declare_ a part that is not already subject to the Section 232 parts tariff, is not in chapters 72, 73 or 76, and is certified for automobile or MHDV production or repair in the United States, as subject to that tariff. HTS headings (from November 1, 2025; CBP CSMS # 66665333): 9903.94.07 (25%, note 33(p)), the deal headings 9903.94.44/.45 (EU), .54/.55 (Japan), .64/.65 (South Korea), .68/.69 (Taiwan, from May 1, 2026) (15% total, note 33(r)), 9903.94.33 (UK parts certified for UK automobiles, 10% total, note 33(q)), 9903.74.09 (MHDV parts, 25%, note 38(j)); USMCA-qualifying certified parts: 9903.94.06 / 9903.74.10, no duty (notes 33(h)(i), 38(k)).
- **Why an importer elects it.** The certified entry does not pay the Section 232 metals duties, the Canada/Mexico duties or the wood duties (notes 33(p)(1)–(4), 38(h)), and no 2026 Section 301 or Brazil duty (notes 52(f)(3)/(6), 50(a)(vi)(3)/(6)).
- **How it is modelled.** Facts `certifiedVehiclePartElection`, `certifiedUkAutoPartElection`, `certifiedMhdvPartElection` (all default **no**: unanswered = the ordinary duties). The MHDV records carry `factsFalse` on the automobile elections (one part, one certification). The 52(f) / 50(a)(vi) reliefs are separate records on the same facts.
- **Coverage.** Chapters 39–97 except 72, 73, 76, minus the listed parts provisions each heading excludes (33(g) and 38(i); for 9903.94.33, 33(j) and 38(i)) and minus the vehicles themselves (33(b), 38(b), 38(c)). Chapters 1–38 (animal, vegetable, food, mineral and chemical products) are left out: note 33(f) defines automobile parts as engines and engine parts, transmissions and powertrain parts, electrical components and parts of vehicles, which classify in the article chapters. `calc-readiness.ts` (`CERTIFIED_PARTS_CHAPTERS` / `exceptRefs`) and `measures_s232_vehicles.py` use the same rule.
- **Review points.** CSMS # 66665333 lists 9903.94.07 for "all countries except" the EU, Japan and the UK, but the heading text excepts only 9903.94.33 (UK parts certified for _UK_ automobiles); a UK part certified for U.S. production is modelled under 9903.94.07.

### China Section 301: review notes

- **Coverage:** Lists 1, 2, 3, 3-described and 4A cover all chapters, at 25/25/25/25/7.5%. Note 20(g) and 20(s)(ii) are modelled as an 8-digit include plus 10-digit carve-outs.
- **Exclusions:** only those in effect (per the compiler's note in 20(a)) are extracted. They currently end **2026-11-09**, so re-check USTR before then.
- **Stacking with 9903.05.31 (12.5%):** additive, per note 52(a). Note 52(f) removes the 12.5% for goods under the named Section 232 headings (metals, vehicles and parts — including the certified parts — wood, semiconductors, patented pharmaceuticals), for every country.
- **Cranes and chassis:** the duties (9903.92.10, 9903.91.12, 9903.91.14) apply only when the importer confirms the described product.
- **Re-check dates:** 2026-11-10 (the maritime action starts) and 2027-06-23 (the 9903.91.05 increase, whose rate is not announced yet).

## 3. Review

Open a PR with the regenerated JSON and SQL (plus `measures.json` changes). Reviewers check:

1. **`ch99-headings.json` diff** — new / removed / re-rated headings match the HTS Change Record for the revision; spot-check the countries and exceptions of the headings measures use.
2. **`measures.json`** — every measure has an official source (`federalregister.gov`, CBP CSMS, `hts.usitc.gov`), `effectiveFrom` (and `effectiveTo` if it ended), `htsEdition` = the headings file edition, and `ch99Code` / `replacesCodes` that exist in `ch99-headings.json` (`tariff:build-data-sql` warns otherwise and fails on invalid rate kinds, dates or duplicate keys).
3. **The SQL file header** — edition, source URL, counts, and any `NOTE` (e.g. "measures.json not found — tariff_measures is emptied"). The body is generated; don't hand-edit it — fix the JSON and regenerate.

The data SQL is one transaction:

1. `DELETE` + `INSERT` all `koala_gains` rows of `tariff_chapter99_headings` and `tariff_measures` (rows sorted, ids from `gen_random_uuid()`), so the tables always equal the committed JSON.
2. Stage the edition's numbered HTS rows in a temp table and `UPDATE hts_codes` where `general_rate_of_duty` / `special_rate_of_duty` / `column2_rate_of_duty` / `unit_of_quantity` differ (`IS DISTINCT FROM`), matched on `hts_number`. Formats mirror the original CSV ingest: trimmed text, blank → `NULL`, units as a `TEXT[]` (`{"No.","kg"}`). New HTS lines are **not** inserted and lines the edition dropped are **not** deleted — the SQL prints both counts; sync the lines with `pnpm tariff:build-hts-lines-sync-sql` (see "Syncing hts_codes lines with a new HTS edition").
3. `SELECT` the counts, then `COMMIT`.

It is safe to re-run: the replace is idempotent and the `hts_codes` update only touches differing rows.

## 4. Merge, then apply

1. **Merge the PR.** The `migrate` job of `insights-ui-deploy-aws.yml` applies pending Prisma migrations (e.g. the one that creates the two tables) before the deploy. Wait for it to finish.
2. **Dry run.** GitHub → Actions → **"insights-ui: apply data SQL"** → _Run workflow_ on `main` with
   `sql_file = insights-ui/prisma/data-sql/tariff-calculator/<file>.sql`, `dry_run = true`.
   The workflow checks the path is under `insights-ui/prisma/data-sql/`, that the file is a single `BEGIN; … COMMIT;` transaction, then runs it with its `COMMIT` replaced by `ROLLBACK` and prints the counts. Expect: headings = the file's heading count, measures = its measure count, "hts_codes rows updated" = how many base lines changed since the last refresh (0 on a re-run).
3. **Real run.** Same inputs with `dry_run = false` (`psql -v ON_ERROR_STOP=1 -f <file>`; any error aborts and rolls back the whole transaction).
4. Check the calculator on a few known shipments (the golden scenarios) against the chapter pages' Rates-by-country matrix.

The workflow uses the `DATABASE_URL` repository secret (the same one the deploy's `migrate` job uses), strips Prisma-only URL parameters (`schema`, `connection_limit`, …) before handing it to `psql`, and never prints it.

## Syncing hts_codes lines with a new HTS edition

The base-rate SQL only _reports_ "HTS rows not in hts_codes" and "hts_codes rows not in this edition". To add and remove the lines themselves, run `pnpm tariff:build-hts-lines-sync-sql`. Unlike the other generators it **reads the database** (read-only `findMany`, never writes), because the SQL depends on which rows and header ids exist now:

```bash
# from insights-ui/ — DOTENV_CONFIG_PATH points at an env file with DATABASE_URL (read-only use)
DOTENV_CONFIG_PATH=.env pnpm tariff:build-hts-lines-sync-sql \
  --hts-file ~/Downloads/hts_2026_revision_21_json.json \
  --rollback-out /tmp/hts-lines-sync-rollback.sql
#   --date YYYYMMDD   filename prefix (default: today, UTC)
#   --out <path>      different output path
```

Output: `prisma/data-sql/tariff-calculator/<YYYYMMDD>-<edition-slug>-hts-lines-sync.sql` (committed) and the rollback file (**not** committed — it holds a full copy of the deleted rows and their candidate-code links; keep it until the sync has been checked in production). The same inputs and database state give byte-identical files.

How rows are matched (mirrors the original per-chapter CSV ingest, commit `cca8b5131`):

| Rule                   | Detail                                                                                                                                                                                                                                                                                                                                                                                                             |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Chapter                | Numbered rows: the first two digits. Unnumbered header rows: the chapter of the next numbered row (chapter-leading section headers such as "I. CHEMICAL ELEMENTS" belong to chapter 28, not 27).                                                                                                                                                                                                                   |
| `sort_order`           | 0-based position within the chapter, in the edition's order.                                                                                                                                                                                                                                                                                                                                                       |
| `parent_id`            | The most recent row with `indent - 1`, using the original ingest's indent stack (cut back at every row). Indent-0 rows, chapter-leading section headers, and rows below an indent gap in the edition (e.g. `2620.99.75` at indent 3 → `2620.99.75.20` at indent 5) get `NULL` — exactly what the ingest stored (the generator checks that this rule reproduces every current `parent_id` before writing anything). |
| Formats                | Description trimmed; rate / quota / additional-duty cells trimmed, blank → `NULL`; units → `TEXT[]`; `hts_code_10` = the digits of 10-digit lines.                                                                                                                                                                                                                                                                 |
| Existing numbered rows | Matched by `hts_number`. Their `indent` and `description` are synced to the edition too (rates are the base-rate SQL's job).                                                                                                                                                                                                                                                                                       |
| Existing header rows   | Matched by indent + whitespace-normalized description in sequence order (an LCS over the chapter's rows, numbered rows acting as anchors), referenced by id. Unmatched ones are deleted / inserted.                                                                                                                                                                                                                |

Only chapters with a difference (new / removed rows, changed indent, description, order or parent) are touched. The transaction:

0. **Guard** — aborts unless each affected chapter still holds exactly the snapshot's row ids in the same order. A stale file, or a second run after it was applied, fails instead of doing damage: regenerate instead.
1. Stages the affected chapters' edition rows in a temp table keyed by (chapter, position), with each row's parent position, and resolves each to its existing id or a new `gen_random_uuid()`.
2. Deletes the rows the edition dropped (numbered by `hts_number`, headers by id) — their `hts_code_candidate_codes` links cascade; the count is printed first.
3. Inserts the new rows (all columns in the formats above).
4. Re-sequences `sort_order` and re-points `parent_id` (plus `indent` / `description`) for every row of those chapters — only differing rows are written.
5. Integrity checks, printed and asserted (a failing one raises and rolls everything back): per-chapter row count = edition; no duplicate `sort_order`; every row at its edition position; every parent in the same chapter, one indent up and above the row; every `parent_id` = the indent-stack parent; no numbered row outside the edition in the affected chapters; overall numbered diff 0 missing / 0 extra.

Before writing the SQL the generator simulates the post-sync state in memory and asserts the same rules on **every** chapter; it refuses to write the file if any fails. Apply it like any data SQL (§4, dry run first). For HTS 2026 Revision 21 (`20261010-2026-revision-21-hts-lines-sync.sql`): 27 chapters, +363 / −86 numbered lines, +41 / −9 header rows, 9 re-indented and 43 re-described rows, 14,264 candidate-code links removed with the deleted lines.

**Rollback** (after a committed sync): run the rollback file through the same workflow. It deletes the inserted rows (numbered by `hts_number`; headers by chapter + post-sync `sort_order` + indent + description), re-inserts the deleted rows and their links with their original ids and columns, restores every pre-sync row's `sort_order` / `parent_id` / `indent` / `description` / `updated_at`, and checks each chapter's ids and order equal the snapshot. Links only restore while their `tariff_candidate_codes` rows still exist. The rollback file lives outside the repo, so to run it with the workflow, copy it into `prisma/data-sql/` on a branch at that time.

**Page impact.** `/hts-codes/us/[section]/[chapter]` lists a chapter's rows in `sort_order` (anchors are `#<hts_code_10>`; there are no per-line URLs, so nothing 404s). New lines appear and removed ones disappear once the chapter's cache is invalidated — the pages are cached by tag, so after the real run use **Invalidate Cache** in each affected chapter page's admin menu (or wait for the next deploy). Calculator search (`/api/tariff-calculator/hts-search`) reads `hts_codes` directly: removed codes are no longer found (correct — they are not valid for entry under this edition), new codes are found, and breadcrumbs follow the corrected `parent_id` chain. New lines have no candidate-code links until the candidate-code ingest runs for them.

## Statistical numbers the HTS JSON doesn't print (Chapter 91 statistical note 1)

**The gap.** The USITC HTS JSON prints 95 Chapter 91 subheadings as 8-digit lines with a rate, no units and no 10-digit rows. These are the compound-rate watch, clock and movement lines: 9101.11.40, 9102.11.10 to 9102.29.60, 9102.91.x, 9103.x, 9104.00.05 to .60, 9105.11 to 9105.99.40, 9106.90.55, 9108.11 to 9108.19 and 9109.10.x. Every 10-digit line in the HTS JSON is printed. A scan of 2026 Revision 21 finds no other rated 8-digit line without 10-digit rows in chapters 01–97. Chapters 98 and 99 have such lines, but they are special provisions, not calculator lines. Without their own rows:

- the calculator answered "We couldn't find HTS code 9102.11.10.xx";
- chapter generator lines and grids skipped them;
- `rate-strings.json` and `program-coverage.json` skipped them, so readiness counted 82 of chapter 91's lines.

**What the HTS says.** Chapter 91 statistical note 1 defines the 10-digit numbers ([2026 Revision 21, Chapter 91](https://hts.usitc.gov/reststop/file?release=2026HTSRev21&filename=Chapter%2091)):

- Each article is "constructively separated into its component parts", and each component is valued separately. The values add up to the article's value.
- The importer combines the 8-digit subheading with a component suffix. For example, 9102.11.10 + 10 is the movement, 20 the case, 30 the strap, band or bracelet and 40 the battery.
- Every named component is reported, at zero quantity and value when it is not in the shipment.

CBP rulings apply the subheading's rate across those numbers:

- [N362026](https://rulings.cbp.gov/ruling/N362026) (Swiss automatic watches): 9102.21.7010 movement $1.53 each, .7020 case 4.2%, .7030 strap 9.8%.
- [H326900](https://rulings.cbp.gov/ruling/H326900): duty is assessed on the component values the note requires.
- [H305372](https://rulings.cbp.gov/ruling/H305372): note 1(c) suffixes.

**Design.** These numbers are real statistical reporting numbers, so we use them and never invent a key such as `…00`:

| Where                  | How                                                                                                                                                                                                                                                                                                                                                                                                                            |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Reviewed data          | `src/tariff-data/calculator/statistical-suffixes.json`: note 1(a)–(r) transcribed. Each scheme has its subheadings and rows (suffix, description, unit, depth for "Travel clocks:" / "Other clocks:" groups), plus the sources. Helpers are in `src/utils/tariff-calculator/statistical-suffixes.ts`.                                                                                                                          |
| Edition rows (scripts) | `lib/statistical-suffix-rows.ts` `withStatisticalSuffixRows` adds the component rows after each listed subheading. They are one level deeper per group and have blank rates, inherited from the subheading like any statistical row. `editionByChapter` (the lines sync, `rate-strings.json`, `program-coverage.json`) and `extractBaseRateRows` (the base-rate SQL) use it. It throws when the edition and the JSON disagree. |
| `hts_codes`            | `20261013-2026-revision-21-hts-lines-sync-ch91-statistical-suffixes.sql` (lines sync, chapter 91 only): +293 numbered rows (`hts_code_10` set) and +35 group rows, nothing deleted, chapter re-sequenced (314 → 642 rows). The `/hts-codes` chapter 91 page shows them under their subheading.                                                                                                                                 |
| Calculator             | Every number of a subheading loads the subheading's rate: `loadMeasureEngineLine` walks up `parent_id`, and falls back to the 8-digit row until the SQL is applied. The rate is priced **once on the whole article**, with `componentValuesUsd` (case / strap, band or bracelet / battery / movement …). The base line carries a note naming the subheading's suffixes. Search finds the numbers once the SQL is applied.      |
| Chapter generator      | `rate-table.ts` keys the 8-digit row as a line by its **first** statistical number (9102.11.10 → `9102111010`), so there is one line per subheading in the matrix, `tariffUpdates.lines` and `tariffEngineering.lines`. The chapter page shows `9102.11.10`; its calculator link opens `9102.11.10.10`.                                                                                                                        |

Per HTS revision:

1. Check statistical note 1 against `statistical-suffixes.json` and update `htsEdition` / `reviewedAt`. The scripts refuse an edition whose 8-digit leaves don't match the file.
2. Rebuild:
   - `rate-strings.json`: `pnpm tariff:rate-parse --hts-file …`;
   - the program coverage lines: `pnpm tsx src/scripts/tariff-calculator/extract-ch99-program-coverage.ts --lines-only --hts-file …`.
3. Regenerate the lines sync.

"¢/jewel over 7" rates (chapter 91 clocks: the general rates of 9105.19.30 and 9105.29.30; the column 2 rate of those two and of 9105.99.40) are read by the shared parser as a per-jewel charge with a threshold (`PerUnitCharge.overThreshold`, `chargedQuantity` in `shipment-duty.ts`). The charge is the rate × (`NO:jewels` − 7 × `NO`), never below 0. `NO:jewels` is the total number of jewels in the shipment's movements and `NO` is the number of movements (the "each" quantity). This equals the per-movement count when every movement has the same number of jewels; enter one line per jewel count otherwise. A missing jewel or movement count is a "Quantity required" error. The base line note shows the arithmetic. The generator and `validate-chapters --check-calculator` price it at the nominal 1,000 movements with 17 jewels each (`thresholdNominalQuantities`: threshold + 10), so the jewel part is compared too. Golden scenario: `ch91-jeweled-travel-clock-cn`.

#### Rate parseability (`pnpm tariff:rate-parse`)

The engine prices a line's base rate (general; column 2 for Cuba / North Korea / Russia / Belarus; the special rate of a claimed program) with the shared parser in `src/utils/tariff-reports/shipment-duty.ts`. A rate it can't read — or reads into a unit the calculator can't ask a quantity for — fails every shipment of the line, so the chapter is **NOT READY** (`UNPRICED`) unless a `kind: "rates"` waiver accepts it. Special rates count only for programs that aren't lapsed (those the calculator would offer as a claim).

```bash
pnpm tariff:rate-parse                                   # unpriceable rate strings per chapter (UNPRICED / ACCEPTED)
pnpm tariff:rate-parse --chapter 17                      # one chapter (exit 1 if it has an unaccepted one)
pnpm tariff:rate-parse --hts-file <HTS JSON>             # rebuild src/tariff-data/calculator/rate-strings.json first (per HTS revision)
```

`rate-strings.json` holds each chapter's distinct rate strings with a line count and an example line (CI is offline). Each 10-digit line takes its rates from the nearest row up its indent hierarchy with a general rate, as `loadMeasureEngineLine` does; where the edition skips an indent level the 8-digit subheading is used and the rebuild lists those lines (check their `hts_codes.parent_id`).

Units the parser understands (keys the engine's `quantities` take, see `src/utils/tariff-calculator/rate-units.ts`):

- Plain: `KG`, `CKG`, `G`, `T`, `L`, `PF.L`, `NO` (head / each / article), `DOZ`, `DPR`, `PRS`, `GROSS`, `M` (incl. "lin. m"), `M2`, `M3`, `BBL`, `THS`.
- **Per 1,000** ("89.6¢/1000", "$2/1,000", "$2.50/thousand"): the amount is divided by 1,000 and charged per unit, so the quantity is the plain count in `NO` (500,000 bulbs → 500,000 × $0.000896 = $448), matching the lines' "No." reporting unit. "10¢/1,000 pins" → `NO:pins`.
- Thresholds: "2.8¢/jewel over 7" → `NO:jewels` above 7 per movement (`NO`), see "Statistical numbers the HTS JSON doesn't print".
- **Qualified quantities** get their own key — the base code plus the qualifier — because they are a different number from the plain weight: `KG:gross weight` ("on contents and container", ", including weight of container" — gross weight incl. the immediate container), `KG:drained weight`, `KG:entire contents` ("on entire contents of container"), `KG:total sugars`, `KG:<metal> content` ("on molybdenum / tungsten / copper / lead / zinc / … content"; the HTS reporting units "Mo kg", "W kg", "Cu kg" … map to these), `KG:anhydrous morphine content`, `M2:recording surface`, `GROSS:immediate containers`, `NO:jewels`, `NO:packs`. The rate text's own wording ("kg on molybdenum content") is accepted as a key too. A qualified rate never falls back to the plain key: missing it is a "Quantity required" error naming the qualified unit. "pf. liter on ethyl alcohol content" is plain `PF.L`.

- Also read: "+" with or without spaces ("15.4¢/kg +59%"), "33 1/3%", "6.5% on the entire set", line-break hyphens ("thou- sand"), "0.2¢ for each other piece or part" (`NO:other pieces or parts`), buttons' "0.3¢/line/ gross" (`GROSS:size in lines` — the size in lines × the number of gross, the HTS reporting unit "gr.lines"), and the raw-sugar polarity formula (chapter 17; optional `polarityDegrees`, priced at 100° without it).

### 2. Close the gaps

Model each `GAP` program in `build-measures.py` (§2), regenerate `measures.json`, and re-run the check until the chapter is **READY**. Add at least 3 golden scenarios for the chapter in `golden-scenarios.json`, including a China-origin case, and run `pnpm tariff:calc-scenarios`.

**Waivers** (`src/tariff-data/calculator/accepted-gaps.json`) are for gaps a reviewer explicitly accepts — never to get a chapter switched on faster. Each entry has `id`, `kind`, `ch99Codes`, `linePrefixes` (empty = every line), `chapters` (empty = any), `conditionNotModelled`, `reason`, `sources`, `reviewedBy`, `reviewedAt` and `reviewBy` (ISO date, at most ~90 days out):

- `kind: "lines"` — the listed unmodelled lines report `ACCEPTED` instead of `GAP` until `reviewBy`.
- `kind: "condition"` — the heading is modelled, but a condition the line-level check can't see is not (e.g. 9903.85.68 reaching non-Russian goods made with aluminum smelted or cast in Russia). It never accepts an unmodelled line; it is listed with the chapters it touches.
- `kind: "rates"` — unpriceable base-rate strings whose whole text matches `ratePattern` (a case-insensitive regex) in `rateColumns` (`general` / `column2` / `special`; empty = all) of `chapters` report `ACCEPTED` instead of `UNPRICED`. `ch99Codes` / `linePrefixes` stay empty.

After `reviewBy` a waiver stops applying (the check prints `WAIVER EXPIRED`) and the gap blocks again until someone re-reviews it and moves the date. A waiver that matches nothing is reported so it can be removed.

### 3. Switch it on (or off)

1. Update the `calc-enabled-chapters` line above in the same PR as the measures (CI fails if it lists a NOT READY chapter; `pnpm tariff:validate-chapters --check-calculator` checks it too, plus `appConfigDefaults.json`).
2. After the data SQL is applied (§4), edit **`TARIFF_CALC_MEASURES_ENABLED`** in Admin → App Settings (e.g. `1,30,39`). It applies within about 30 minutes (App Settings cache); no deploy is needed.
3. Check a few golden scenarios for the chapter on the live calculator.
4. To switch the engine off for every chapter, set the value to `off` (the screen can't save an empty value); to drop one chapter, remove it from the list. Update the documented line above to match.

## Weekly freshness check (`pnpm tariff:freshness`)

A scheduled job tells you **when** to run this runbook. It only reports — it never edits data or touches the database; a person reviews each item and applies it through the steps above (and [chapter-content-refresh.md](chapter-content-refresh.md) for the chapter pages).

- **Workflow:** `.github/workflows/insights-ui-tariff-freshness.yml` — Mondays 13:00 UTC, plus _Run workflow_ (inputs: `days` look-back, `create_issue`). The report is always in the run's job summary.
- **Issue:** when there is something to report it opens one issue titled **"Tariff data freshness: updates to review"**. While that issue is open, later runs add a **comment** to it instead of opening another (matched by exact title among open issues). Close it once every item is applied or dismissed; the next finding opens a fresh issue. Nothing to report → no issue, no comment.
- **Script:** `src/scripts/tariff-calculator/check-data-freshness.ts` (imports only Node built-ins + `lib/hts-source.ts`, so CI runs it with `npx tsx` without installing the workspace).

```bash
# from insights-ui/
pnpm tariff:freshness                       # markdown report on stdout
pnpm tariff:freshness --out /tmp/fresh.md   # also write it to a file
pnpm tariff:freshness --json                # JSON (hasFindings, hts, federalRegister, upcomingMeasures, errors)
pnpm tariff:freshness --days 30             # Federal Register look-back (default 8: weekly run + 1 day overlap)
pnpm tariff:freshness --since 2026-10-01    # explicit start date
pnpm tariff:freshness --horizon-days 30     # measure-date look-ahead (default 14)
pnpm tariff:freshness --today 2026-11-01    # pretend today is this date
```

What it checks:

1. **HTS revision** — the edition `https://hts.usitc.gov/reststop/releaseList` marks `current` (shared helper `fetchCurrentHtsRelease()` in `lib/hts-source.ts`, also used by `pnpm tariff:validate-chapters --check-hts`) against every edition the committed data records: the top-level `htsEdition` of each `src/tariff-data/calculator/*.json`, `tariffUpdates.now.edition` of the chapter files, and the edition in the newest `prisma/data-sql/tariff-calculator/*.sql` filename. Any file on an older edition is listed → regenerate per §1–4.
2. **Federal Register** — documents published in the look-back window from the [Federal Register API](https://www.federalregister.gov/developers/documentation/api/v1) (no key): all USTR documents; presidential documents mentioning "Harmonized Tariff Schedule" / "Chapter 99" / "Section 301" / "Section 232"; BIS documents mentioning "Section 232"; CBP documents mentioning "Chapter 99" / "Section 301" / "Section 232"; and any agency's document mentioning both "Chapter 99" and "Harmonized Tariff Schedule". Each shows date, type, agency, document number + FR citation, link and title. Documents whose number already appears in a `federalregister.gov` URL in the calculator or chapter JSON are listed separately as "already cited". For the rest: does it add, change or end a duty on a covered chapter? If so, update the definitions in `build-measures.py` / the chapter files.
3. **Scheduled dates** — measures in `measures.json` whose `effectiveFrom` or `effectiveTo` falls within the horizon, grouped by date / program / Chapter 99 heading. Check the step is still on schedule (no delay or extension published) and shows up on that date.

A source that is down (timeout, HTTP error, bad JSON) becomes a line under **"Check errors"** and counts as a finding, so an outage shows up in the issue instead of failing silently. Network calls time out (20 s release list, 30 s per Federal Register page, one retry). The script exits 0 whenever it produced a report (1 only for bad arguments or unreadable data files).

## Gaps / things the scripts don't do

- **Not modelled (issue #1796):** the import adjustment offsets (Proclamations 10925 / 10984: company-specific credits), knock-down kits, polysilicon (9903.45.33, Proclamation 11052; not in Revision 21), drone Annex III components (from 2027-02-09). Russia 9903.85.67/.68 is modelled for products of Russia only; the "smelted or cast in Russia" reach for other origins is an accepted gap.

- **Coverage** (which HTS lines a measure covers) is not in the HTS JSON — it lives in the Chapter 99 U.S. notes text and is curated into `measures.json`.
- `9903.92` (a header row, not a 10-character heading) is skipped; its indented headings (`9903.92.10`, `9903.92.80`) inherit its countries.
- Headings whose country wording is unusual (e.g. "any country other than …") are not parsed as exclusions; the measure in `measures.json` must set `countriesExclude`.
- New / removed HTS lines in `hts_codes` are not handled by the base-rate SQL (it only reports them) — use `pnpm tariff:build-hts-lines-sync-sql` (see "Syncing hts_codes lines with a new HTS edition").
